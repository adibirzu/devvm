Everything you (Royce) need to connect to the shared OCI dev VM and start working
**alongside the team on the same server** — durable AI agent sessions, shared pairing,
and per-account git identity.

> - VM (WireGuard server) address: `10.200.200.1`
> - VM public IP / WG endpoint: `<VM_PUBLIC_IP>` — **provided in your `client_royce.conf`** (ask the admin; never commit it)

## 1. One-time prerequisites (macOS)

```bash
brew install wireguard-tools mosh
```

- `wireguard-tools` gives you `wg-quick` (use the **CLI**, not the GUI app — the repo helper drives `wg-quick`).
- `mosh` keeps your shell alive across sleep, Wi-Fi changes, and roaming — essential for long agent sessions.

Place the admin-provided config where the repo helper expects it (or keep it anywhere and use `wg-quick` directly):

```bash
# Option A — via the repo (reads configs/wireguard/client_royce.conf):
#   put client_royce.conf at  oci-remote-dev/configs/wireguard/client_royce.conf
# Option B — keep it anywhere, e.g. ~/wg/client_royce.conf, and use the direct command in step 2.
```

## 2. Bring the WireGuard tunnel up

```bash
# Option A — repo helper (auto-loads configs/wireguard/client_royce.conf):
./scripts/connect.sh -u royce wg-up

# Option B — directly against the file the admin gave you:
sudo wg-quick up ~/wg/client_royce.conf

# Confirm the tunnel is live:
ping 10.200.200.1            # should reply through the tunnel
./scripts/connect.sh -u royce wg-status     # or: sudo wg show
```

Bring it down when you're done: `./scripts/connect.sh -u royce wg-down`  (or `sudo wg-quick down ...`).

Split-tunnel is the default — only VM-subnet traffic goes through WireGuard; the rest of your
network is untouched.

## 3. Connect to the VM

Prefer **mosh** for anything involving an agent session (survives disconnects):

```bash
mosh --ssh="ssh -i ~/.ssh/<royce_key>" royce@10.200.200.1
# plain SSH also works:
ssh -i ~/.ssh/<royce_key> royce@10.200.200.1
```

> Tip: add a `~/.ssh/config` block so you can just type `ssh devvm`:
> ```
> Host devvm
>     HostName 10.200.200.1
>     User royce
>     IdentityFile ~/.ssh/<royce_key>
> ```

## 4. Verify your identity on the VM

```bash
whoami            # -> royce
git-whoami        # shows the git author/email enforced for your account
```

Your git `user.name` / `user.email` are pre-set per account and **enforced** via `GIT_AUTHOR_*`
in `~/.bashrc`, so even in shared repos your commits attribute to you.

## 5. Set up your own GitHub identity (never a shared token)

```bash
unset GITHUB_TOKEN          # a stray env token overrides stored creds — clear it first
gh auth login               # interactive, per-account creds land in ~/.config/gh
# (or drop your GitHub SSH key at ~/.ssh/id_github and use SSH remotes)
```

Each developer authenticates as themselves — there is **no shared GitHub token** on the VM.

## 6. Durable agent sessions (survive disconnects, reboots, network drops)

Use `agentctl` so your AI coding session keeps running even if your laptop sleeps or the link drops:

```bash
# Start a session for a project (claude / codex / gemini etc.)
agentctl start claude -p myproject -d ~/myproject

# See your sessions and their state
agentctl ls

# Attach to a running session  (detach with: Ctrl-b then d)
agentctl attach 'agent:myproject:claude'

# After reconnecting, list sessions + open threads to pick up where you left off
agentctl resume

# Other lifecycle verbs:
agentctl status | logs | stop | restore
```

Sessions are tmux-backed on a per-user group socket (`~/.agentctl/tmux.sock`) and are restored on
reboot, so a VM restart or a dropped tunnel won't lose your work.

---

## 7. Work **together** on the same server (shared / pair session)

For real-time collaboration on one shared AI session:

```bash
# One person starts the shared session:
pair-claude start

# You (and anyone else) join the same live session:
pair-claude join

# Helpers:
pair-claude status        # is a shared session active?
pair-claude note "..."    # drop a shared note
pair-claude summary       # summarize the shared session
pair-claude kill          # end it
```

`pair-claude join` attaches everyone to the **same** AI session over a shared tmux socket — you see
the same output and can take turns driving. Use `agentctl` (section 6) when you want your **own**
isolated durable session instead.

## 9. Configure your agents (inference providers + endpoints)

You manage your own agent configuration. Here's the data your agents need and where it goes.

### Your private service endpoints (over WireGuard)

| Service | URL |
|---------|-----|
| Your code-server (VS Code in browser) | `http://10.200.200.1:8445` |
| Developer dashboard | `http://10.200.200.1` |
| Control plane (health/API) | `http://10.200.200.1:8082` (`/healthz`) |
| Vibe Kanban | `http://10.200.200.1:3000` |
| Claude Code UI | `http://10.200.200.1:3001` |

Quick check from inside the tunnel: `curl -fsS http://10.200.200.1:8082/healthz`.

### Give Hermes an inference provider (required before it can answer)

A fresh Hermes install has **no inference provider** — it will accept input but reply *"No inference provider configured."* Pick one:

```bash
# Option A — a direct API key (fastest). Edit your per-user, chmod-600 env file:
nano ~/.hermes/.env
#   add ONE of:  OPENROUTER_API_KEY=...   OPENAI_API_KEY=...   ANTHROPIC_API_KEY=...
hermes model            # interactively choose provider + model
hermes -z "ping"        # verify you get a real answer back

# Option B — route through the shared MultiLLM gateway (no raw key; uses the VM's
# subscription routing). Only if the gateway service is running on the VM:
#   in ~/.hermes/.env:  OPENAI_BASE_URL=http://127.0.0.1:<gateway-port>/v1
#                       OPENAI_API_KEY=<gateway-token>
#   then: hermes model  (point it at the gateway model)
```

Hermes config lives per-user in `~/.hermes/{.env, SOUL.md, config.yaml}` (keep them `chmod 600`). `agy` and `claude`/`codex` similarly read your own per-user config — never a shared key.

### Telegram bridge — operated by the admin, not you

There's an optional Telegram→VM bridge that lets a chat message drive a durable agent session on the VM. **You don't set this up, and you never touch the admin's machine.** It runs entirely on the admin's own computer (their PAI registers a VM session and types into its tmux pane over SSH).

Your only part is normal VM work: start durable sessions with `agentctl` (Section 6) and configure your own agents (above). If you'd ever like one of *your* VM sessions driven from a chat, ask the admin and they wire it from their side — nothing for you to install or run.

```bash
# Your side is just a normal durable session on the VM, e.g.:
agentctl start hermes -p mywork -d ~/shared-workspace/mywork
agentctl ls          # lists your sessions
```

## 10. Troubleshooting

| Symptom | Fix |
|---------|-----|
| `ping 10.200.200.1` fails | Tunnel isn't up. Re-run `./scripts/connect.sh -u royce wg-up`; check `sudo wg show`. |
| `wg-quick up` says "already exists" | A stale interface — `sudo wg-quick down <conf>` then up again. |
| SSH `Permission denied (publickey)` | Wrong/missing key. Confirm with the admin which key matches your installed pubkey; use `-i ~/.ssh/<royce_key>`. |
| `gh` acts as the wrong user | `unset GITHUB_TOKEN` then `gh auth login` again. |
| Lost your agent session after a disconnect | `agentctl resume` (it survived) — then `agentctl attach '<name>'`. |
| Mosh won't connect but SSH does | Ensure `mosh` is installed on the VM too and UDP isn't blocked; fall back to `ssh` + `agentctl` (the session is durable regardless of client). |
